## 2026-08-19 — Cross-project SIRIUS annotation transfer for the Everything-Bagel features

- **Category**: data-engineering / metabolomics tooling
- **What happened**: The Everything-Bagel feature table (38,547 features) and the sibling EB/MZmine3 table (4,107 features) share MassIVE `MSV000090464` but were generated by different feature finders, so feature IDs do not correspond. SIRIUS results (EB, 2,860 annotated) were transferred onto the local features by matching precursor `m/z` + RT + MS2 spectral cosine instead of re-running SIRIUS.
- **Why it matters**: A naive "just reuse the SIRIUS table" join would have 0 matches; the m/z+RT+MS2-cosine key (ppm 10, rt 0.5 min, cos-min 0.7) recovers 2,182/2,860 EB features → 1,773 local features annotated without spending another SIRIUS run.
- **Resolution**: `analysis/sirius_annotation/scripts/import_sirius_transfer.py` + full write-up in `analysis/sirius_annotation/SIRIUS_ANNOTATION.md`.
- **Tags**: `metabolomics`, `sirius`, `gnps`, `annotation-transfer`, `feature-matching`, `ms2-cosine`

## 2026-08-19 — Everything-Bagel merges isobaric/co-eluting EB features into single features

- **Category**: data-quality / gotcha
- **What happened**: Because the Everything-Bagel alignment is more permissive, 296 local features receive more than one EB source feature; of those, 69 receive hits that **disagree on molecular formula** (e.g. namalide d vs mycalamide A) and must be flagged.
- **Why it matters**: Silently dropping the lower-priority hit loses a real annotation. Any joined/downstream table must treat `merged_conflict == True` features as needing manual review, and keep `sirius_transfer_map.tsv` as the audit trail.
- **Resolution**: `n_sirius_hits` / `sirius_hit_ids` / `sirius_hit_formulas` / `merged_conflict` columns on `sirius_annotations.tsv`.
- **Tags**: `data-quality`, `metabolomics`, `feature-collapse`, `isobaric`, `conflict`

## 2026-08-19 — Everything-Bagel feature MGF has degenerate blocks (CHARGE=0 / PEPMASS=0.0) even for has_ms2=True features

- **Category**: data-quality / gotcha
- **What happened**: In `aligned_features_filled.mgf`, ~1/150 pilot targets (row ID 6813, `has_ms2=True`, charge 1 in the feature table) had a broken MS2 block: `CHARGE=0`, `PEPMASS=0.0`, zero peaks — unusable by SIRIUS. Roughly 31.8k of the 38k MGF blocks carry `CHARGE=0` (fan-out filler blocks for features without a real consensus spectrum).
- **Why it matters**: A blind "export all has_ms2 targets" → SIRIUS pipeline would submit shards containing empty spectra, wasting jobs and confusing results.
- **Resolution**: `export_native_mgf.py` now validates each exported block (CHARGE matches target, PEPMASS>0, ≥1 positive peak), drops failures, and reports which row IDs were excluded.
- **Tags**: `data-quality`, `metabolomics`, `sirius`, `mgf`, `validation`, `everything-bagel`

## 2026-08-19 — Native SIRIUS target set reduces mainly on charge state, not sample presence

- **Category**: metabolomics / SIRIUS scoping
- **What happened**: Counting the un-annotated features with MS2 (4,680) and applying filters: charge 1+ only → 3,927 (SIRIUS 6.3.12 refuses 2+/3+), 1+ with default [M+H]+ adduct only → 3,316, detected in ≥2 of 90 analysis samples → barely removes anything (median detection is 59/90 samples).
- **Why it matters**: For deciding "how many features to run", charge state is the lever that matters; sample-presence filtering is a no-op on this dataset and should not be used as the reducer.
- **Resolution**: Native run targets the 3,927 charge-1+ features; per-shard jobs of ~30 spectra handle failure/restart.
- **Tags**: `metabolomics`, `sirius`, `scoping`, `feature-selection`

## 2026-08-19 — Everything-Bagel aligned_features.csv area columns differ from the EB quant schema

- **Category**: data-engineering / gotcha
- **What happened**: EB's `gnps_ms2_quant_full.csv` stores areas as `datafile:<stem>.mzML:area` columns; the Everything-Bagel `aligned_features.csv` uses `<stem>.mzML Peak area` (with a literal space) plus richer metadata columns (`row m/z`, `row retention time`, `charge`, `adduct`, `parent_mass`, `has_ms2`, …). The Bsal `_spores` → `_spore` mapping is directional (Bd singular, Bsal plural) and matches between curated metadata and the FBMN table (123/123 stems align), so stems must be matched verbatim, never normalized.
- **Why it matters**: Porting EB's ordination/differential scripts requires a schema adapter only in `build_ordination_table.py`; the downstream `linked_data/` schema (row_id, mz, rt + per-sample cols) is unchanged, so the PCoA/differential scripts run verbatim.
- **Resolution**: `analysis/ordination/scripts/build_ordination_table.py` now reads `aligned_features.csv` (rename `row ID/row m/z/row retention time` → `row_id/mz/rt`, strip ` Peak area` + `.mzML` from area col names).
- **Tags**: `data-engineering`, `everything-bagel`, `feature-table`, `schema`, `porting`

## 2026-08-19 — Everything-Bagel ordination results replicate EB's matrix-dominance finding despite ~9.8x more features

- **Category**: analytical-concordance
- **What happened**: The bagel pipeline (38,547-feature table) reproduces the EB biological hierarchy: PCoA axis1 62.9% (all) / 75.9% Bd / 70.6% Bsal, and per-comparison n_significant rank-order vs EB is nearly identical (Spearman rho 0.985 Bd, 0.996 Bsal); liq-vs-liq life-stage contrasts stay ~0 significant in both. Absolute counts scale ~9.8-9.3x with the larger feature set.
- **Why it matters**: The Everything-Bagel feature table is a different (much denser) feature universe, but the qualitative story — matrix dominates, life stage within liq is weak — is unchanged, giving confidence in the biological signal.
- **Resolution**: Findings file `.living/findings/matrix-dominates-bagel-metabolome.md`; comparison_*_vs_* summaries under `analysis/differential_features/`.
- **Tags**: `analytical-concordance`, `ordination`, `differential-abundance`, `everything-bagel`, `eb-comparison`

## 2026-08-20 — Sporangium-vs-Mature within-matrix = 0 significant features justifies the collapse, but the life-stage signal concentrates in the spore fraction

- **Category**: analytical-design
- **What happened**: The user's hypothesis (sporangia and mature are very similar → collapse for power) is empirically supported: every within-matrix Sporangium-vs-Mature pairwise contrast in the 30-way scan was 0-significant. After collapsing to stage_group (Zoospore | Developed), the life-stage contrasts show a strong asymmetry: spore fraction has 5.6k (Bd) / 7.2k (Bsal) FDR-significant features, while the liquid fraction has only 536 / 54 — the developmental signal is cell-associated, not in the supernatant.
- **Why it matters**: The main biological contrast (zoospore vs the rest) should be read in the spore fraction; in the liquid, life stage barely reshuffles the (media-dominated) chemistry, matching F-002's matrix dominance. The liq-vs-spore secreted_vs_cellular family is the correct place to hunt secreted/bioactive compounds, plus life-stage hits that are also liq-enriched.
- **Resolution**: `analysis/differential_features_primary/` script + `DIFFERENTIAL_FEATURES_PRIMARY.md`; finding F-003.
- **Tags**: `analytical-design`, `differential-abundance`, `life-stage`, `collapse`, `spore-fraction`, `secreted-compounds`, `everything-bagel`

## 2026-08-20 — Condition vocabulary for the collapsed stage design: `stage_group`/`condition_group` columns on linked_data

- **Category**: data-schema
- **What happened**: The 6-state `condition` (matrix_life_stage, e.g. `liq_Mature`) is the raw sampled condition; to express the hypothesis design reproducibly, `build_ordination_table.py` now also writes `stage_group` (Zoospore | Developed) and `condition_group` (matrix_stage_group, e.g. `spore_Developed`). Sample counts verified: per species liq = 10/20 (Zoo/Dev), spore = 5/10.
- **Why it matters**: Downstream scripts select groups by `condition_group` so the collapse is a first-class, documented schema decision rather than a string `.str.contains()` hack scattered across scripts; the raw 6-state condition is preserved for the exploratory tier.
- **Resolution**: Columns on `analysis/ordination/linked_data/sample_metadata.csv`; consumed by `differential_features_primary.py` and the new PCoA `stagegroup`/`condition` figures.
- **Tags**: `data-schema`, `life-stage`, `collapse`, `sample-metadata`, `everything-bagel`

## 2026-08-20 — Feature-table HTML ported from Rhodotorula, but this project's tables are ~17x bigger

- **Category**: analytical-design
- **What happened**: Ported the Rhodotorula `generate_compound_table_html.py` (self-contained sortable/filterable feature-table HTML, JSON-embedded data, plain-JS sort/filter, identity glyphs, expand-panel details) to the primary-tier significant tables. This project's rollup embeds 103,637 significant rows (~130 MB HTML) vs Rhodotorula's ~6,000-row rollup; even per-contrast tables reach ~28k rows.
- **Why it matters**: The interactive table pattern carries over cleanly, but the document is heavy — browser rendering and the debounced search/sort are still fine but materially slower than the smaller Rhodotorula tables; filtering or opening a specific contrast first is the practical path. It also means the SIRIUS identity is browsable row-by-row (glyph, structure name, NPC class) for manual curation of the 1,106 bioactivity-flagged / 3,003 secreted-candidate hits.
- **Resolution**: `analysis/differential_features_primary/scripts/generate_feature_tables.py` + `pixi run feature-tables-primary`; per-contrast `compound_summary.html`, per-species rollups `all_significant_features_summary_<species>.html` (dendrobatidis 59 MB / salamandrivorans 66 MB — the single combined rollup was ~125 MB and exceeded GitHub's 100 MB per-file hard limit, blocking `git push`), `feature_tables_index.html`.
- **Tags**: `feature-tables`, `html`, `interactive`, `sirius`, `porting`, `everything-bagel`

## 2026-08-20 — GitHub 100 MB per-file limit: chunk generated HTML rollups by species

- **Category**: infra/repro
- **What happened**: `all_significant_features_summary.html` (103,637 rows, ~125 MB, one JSON embed) exceeded GitHub's 100 MB per-file hard limit and rejected `git push` to the new `stajichlab/Batrachochytrium_EB_MS_compare` remote. The commit was rolled back (`git reset --soft HEAD~1`, safe because `main` had no upstream) and the rollup is now emitted per species: `all_significant_features_summary_dendrobatidis.html` (48,867 rows, 59 MB) + `all_significant_features_summary_salamandrivorans.html` (54,770 rows, 66 MB). Per-contrast tables (≤32 MB) and all TSVs (≤32 MB) were already under the limit. The generator script, index hub, and docs were updated; all 25 files re-staged.
- **Why it matters**: GitHub rejects pushes containing any file over 100 MB (hard), and warns above 50 MB. Chunking derived HTML artifacts by an analysis dimension (here `species`) keeps interactive outputs in-repo and pushable without Git LFS or sacrificing the rollup view.
- **Resolution**: edit `generate_feature_tables.py` (split rollup by `df["species"]`, per-species `write_index` links), regenerate via `pixi run feature-tables-primary`, delete the stale combined rollup, re-stage, update `DIFFERENTIAL_FEATURES_PRIMARY.md` / `ANALYSIS_MANIFEST.md`.
- **Tags**: `github`, `git-push`, `file-size-limit`, `feature-tables`, `rollup`, `chunking`
